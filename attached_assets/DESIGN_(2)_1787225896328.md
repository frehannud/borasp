# BoraSP --- Design System & Product Design Specification

> **Projeto:** BoraSP --- Exploração Mobile\
> **Contexto:** Projeto acadêmico / protótipo de aplicativo mobile\
> **Design de referência:** Google Stitch\
> **Implementação:** Replit\
> **Versão:** 1.0\
> **Status:** Protótipo funcional / em desenvolvimento

------------------------------------------------------------------------

## 1. Visão geral

O **BoraSP** é um aplicativo mobile de exploração da cidade de São Paulo
baseado em localização, mobilidade e descoberta de experiências.

A proposta é transformar o deslocamento pela cidade em uma oportunidade
de descoberta. Em vez de o usuário apenas escolher um destino, o
aplicativo ajuda a encontrar **lugares, restaurantes, experiências
culturais e outros pontos de interesse** próximos ao usuário,
considerando sua estação de metrô e seu contexto.

A experiência principal deve ser:

1.  O usuário informa onde está.
2.  O aplicativo identifica uma estação ou região.
3.  O usuário escolhe o tipo de experiência desejada.
4.  O BoraSP recomenda um destino.
5.  O usuário recebe informações objetivas sobre o local.
6.  O usuário pode abrir o destino no mapa ou solicitar outra
    recomendação.

------------------------------------------------------------------------

# 2. Objetivo do produto

### Problema

São Paulo possui uma enorme quantidade de lugares para conhecer, mas
descobrir o que fazer próximo a uma estação ou durante um deslocamento
pode exigir pesquisas em diferentes aplicativos.

### Solução

Criar uma experiência mobile simples que conecte:

-   **Metrô**
-   **Localização**
-   **Interesses do usuário**
-   **Descoberta de lugares**
-   **Recomendações**
-   **Mapa**

### Proposta de valor

> **"Você escolhe onde está e o que quer fazer. O BoraSP encontra o
> próximo lugar para você."**

------------------------------------------------------------------------

# 3. Público-alvo

### Usuário primário

Pessoas que circulam por São Paulo e querem descobrir lugares próximos
às estações de metrô.

Características:

-   Jovens e adultos;
-   Usuários de transporte público;
-   Pessoas que gostam de explorar a cidade;
-   Pessoas procurando restaurantes, cultura e lazer;
-   Usuários que não querem gastar muito tempo pesquisando.

### Contextos de uso

-   "Estou na Paulista. O que posso fazer?"
-   "Estou em Pinheiros e quero comer."
-   "Cheguei em uma estação e tenho 1 hora livre."
-   "Quero fazer algo cultural perto de mim."
-   "Quero descobrir um lugar novo."

------------------------------------------------------------------------

# 4. Princípios de design

## 4.1 Simplicidade

A interface deve reduzir a quantidade de decisões necessárias.

O usuário deve conseguir iniciar uma descoberta em poucos toques.

## 4.2 Exploração

O produto deve transmitir sensação de descoberta, movimento e cidade.

## 4.3 Contexto local

São Paulo deve estar presente na linguagem visual e nas informações
exibidas.

## 4.4 Ação rápida

Cada tela deve possuir uma ação principal claramente identificável.

## 4.5 Mobile first

A experiência foi concebida prioritariamente para telas de smartphones.

------------------------------------------------------------------------

# 5. Identidade visual

A identidade visual utiliza uma combinação inspirada na linguagem visual
do transporte urbano de São Paulo:

-   **Azul:** navegação, confiança, estrutura e ações principais.
-   **Amarelo:** energia, destaque, descoberta e ações de alta
    prioridade.
-   **Branco:** conteúdo e legibilidade.
-   **Cinzas:** informações secundárias e estados neutros.
-   **Preto:** títulos e textos de alta hierarquia.

A interface deve ser visualmente forte, objetiva e funcional.

# 6. Design tokens

> Os valores abaixo são a especificação de implementação baseada no
> protótipo visual do Stitch. Caso o projeto receba tokens oficiais do
> Stitch, estes valores devem ser atualizados para os valores exatos
> exportados.

## 6.1 Cores

  Token                    Valor aproximado   Uso
  ------------------------ ------------------ --------------------------------------
  `color.primary`          `#00549A`          Header, botões principais, navegação
  `color.primary-dark`     `#003F73`          Estados ativos/pressed
  `color.secondary`        `#FFD400`          Destaques, seleção, CTAs secundários
  `color.background`       `#FFFFFF`          Fundo principal
  `color.surface`          `#F7F7F7`          Campos e superfícies secundárias
  `color.text`             `#111111`          Títulos e conteúdo principal
  `color.text-secondary`   `#666666`          Informações secundárias

  `color.success`          `#20A464`          Estados positivos

O amarelo deve ser usado como **cor de destaque**, e não como fundo
dominante de toda a aplicação.

O azul deve funcionar como a principal cor estrutural.

# 7. Tipografia

A interface deve utilizar uma fonte sans-serif moderna e altamente
legível.

### Hierarquia

  Elemento            Peso   Tamanho sugerido
  ------------- ---------- ------------------
  H1                   700          28--32 px
  H2                   700          22--26 px
  H3                   700          18--20 px
  Body                 400          15--16 px
  Body strong          600          15--16 px
  Caption              400          12--13 px
  Button          600--700          14--16 px

### Diretriz

Os títulos devem ser curtos.

Exemplo:

**Bom**

> Onde você está?

**Evitar**

> Selecione abaixo a estação onde você está atualmente localizado.

------------------------------------------------------------------------

# 8. Layout

## 8.1 Estrutura mobile

A aplicação deve utilizar:

-   largura total da tela;
-   conteúdo centralizado;
-   padding lateral de aproximadamente `16px`;
-   cards com espaçamento consistente;
-   header fixo ou visualmente destacado;
-   área inferior reservada para navegação/ações quando necessário.

## 8.2 Espaçamento

Utilizar escala baseada em múltiplos de 4:

``` text
4px
8px
12px
16px
20px
24px
32px
40px
48px
```

### Regra

O espaçamento entre componentes deve ser consistente.

------------------------------------------------------------------------

# 9. Bordas e formas

O protótipo utiliza uma linguagem visual com **bordas fortes e cantos
pouco arredondados**.

### Cards

-   Border: `1px–2px`
-   Radius: `2px–6px`
-   Padding: `12px–16px`

### Botões

-   Border: `1px–2px`
-   Radius: `2px–6px`
-   Altura mínima: `44px`

### Inputs

-   Border visível;
-   Ícone opcional;
-   Placeholder em cinza;
-   Área de toque confortável.

> Evitar excesso de `border-radius: 999px` ou estética excessivamente
> "soft". A interface deve manter personalidade urbana e funcional.

# 13. Loading State

O loading deve aparecer enquanto o sistema procura a melhor
recomendação.

Mensagem principal:

> **Encontrando o melhor pico...**

Mensagem secundária:

> AVALIANDO TRÂNSITO LOCAL

### Objetivo

O estado de loading deve transmitir que o sistema está realmente
processando informações.

### Elementos

-   Ícone/indicador central;
-   Título;
-   Subtexto;
-   Barra ou indicador de progresso;
-   Fundo branco.

------------------------------------------------------------------------

# 22. Ícones

Os ícones devem ser simples, lineares e consistentes.

Categorias recomendadas:

-   Restaurante: fork/knife
-   Cultura: teatro/museu
-   Café: coffee
-   Transporte: train
-   Localização: location pin
-   Busca: search
-   Mapa: map
-   Voltar: arrow-left
-   Fechar: X

### Regra

Não misturar famílias de ícones diferentes.

------------------------------------------------------------------------

# 23. Imagens

As imagens dos locais são fundamentais para a experiência de descoberta.

### Regras

-   Usar imagens reais dos estabelecimentos/pontos;
-   Preferir imagens horizontais;
-   Evitar imagens excessivamente comprimidas;
-   Manter proporção consistente;
-   Usar `object-fit: cover`.

### Recommendation Card

Proporção sugerida:

``` text
16:9
```

------------------------------------------------------------------------

# 24. Microinterações

As interações devem ser rápidas e discretas.

### Seleção

Ao selecionar uma estação:

-   mudança de fundo;
-   pequeno feedback visual;
-   transição de aproximadamente `150–200ms`.

### Botões

No toque:

-   pequena mudança de escala/opacidade;
-   duração curta;
-   retorno imediato.

### Loading

-   animação contínua;
-   evitar animações exageradas.

------------------------------------------------------------------------

# 25. Acessibilidade

A aplicação deve respeitar:

-   contraste adequado;
-   áreas de toque mínimas de aproximadamente `44x44px`;
-   textos legíveis;
-   não depender somente de cor para indicar estado;
-   labels acessíveis para ícones;
-   foco visível quando aplicável.

### Exemplo

Não usar somente:

> "Card amarelo = selecionado"

Também utilizar:

-   borda;
-   ícone;
-   estado textual/semântico.

------------------------------------------------------------------------

# 26. Responsividade

Embora o produto seja mobile-first, a implementação deve suportar
diferentes tamanhos de smartphones.

### Breakpoints sugeridos

``` text
Small mobile: < 360px
Mobile: 360–767px
Tablet: 768–1023px
Desktop: 1024px+
```

No desktop, o aplicativo pode permanecer centralizado em uma largura
máxima semelhante a um smartphone.

# 28. Regras para implementação no Replit

A implementação deve preservar o design do Stitch em vez de
reinterpretá-lo.

## 28.1 Componentização

Separar componentes reutilizáveis:

``` text
Header
StationCard
SearchInput
InterestCard
RecommendationCard
Tag
PrimaryButton
SecondaryButton
LoadingState
EmptyState
ErrorState
```

## 28.2 Tokens

Centralizar cores e medidas:

``` css
:root {
  --color-primary: #00549A;
  --color-primary-dark: #003F73;
  --color-secondary: #FFD400;
  --color-background: #FFFFFF;
  --color-surface: #F7F7F7;
  --color-text: #111111;
  --color-text-secondary: #666666;
  --color-border: #222222;
}
```

## 28.3 Não fazer

Evitar:

-   Gradientes desnecessários;
-   Sombras pesadas;
-   Cards excessivamente arredondados;
-   Excesso de animações;
-   Muitos elementos simultaneamente;
-   Tipografia decorativa;
-   Mudanças de cor sem função.

# 30. Lógica de recomendação

A recomendação pode considerar:

``` text

        +
Categoria selecionada
        +
Distância
        +
Tempo estimado
        +
```

# 34. Direção final de design

O BoraSP deve parecer uma **ferramenta urbana de descoberta**, e não
apenas um aplicativo tradicional de transporte.

A combinação de:

**Azul + Amarelo + Preto + Branco**

deve criar uma identidade forte, simples e imediatamente reconhecível.

A interface precisa responder rapidamente à pergunta:

> **"Estou aqui. O que posso fazer agora?"**

A experiência ideal é:

**Localização → Interesse → Descoberta → Ação.**
